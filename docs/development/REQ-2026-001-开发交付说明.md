## 二、后端 API 一览（挂 `/api/v1/pipeline`，全部需 JWT）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/requirements?page&size&keyword&status&kano_category&priority&aarrr&source` | 需求池分页筛选 |
| GET | `/requirements/:id` | 需求详情（含环节/交付物/审核记录） |
| POST | `/requirements` | 新建需求（自动编号 REQ-YYYY-NNN + 初始化 A~G 环节） |

| DELETE | `/requirements/:id` | 删除（仅 draft/backlog 可删） |

| GET | `/board` | 看板数据（需求列表 + 环节状态 + 统计） |
| GET | `/requirements/:id/stages` | 某需求环节状态 |
| GET | `/requirements/:id/deliverables` | 交付物列表 |
| POST | `/requirements/:id/deliverables` | 登记交付物 |
| DELETE | `/deliverables/:id` | 删除交付物 |
| GET | `/requirements/:id/reviews` | 审核记录 |
| POST | `/requirements/:id/reviews` | 审核（approve 通过 / reject 打回） |

## 三、数据表（启动自动迁移）

1. `ai_pipeline_requirements` — 需求主表（req_no 唯一、卡诺/AARRR/优先级/状态/来源）
2. `ai_pipeline_stages` — 环节表（A~G × 需求，status: todo/doing/done/rework/na）
3. `ai_pipeline_deliverables` — 交付物登记（环节/标题/类型/路径/链接/登记人）
4. `ai_pipeline_reviews` — 审核记录（approve/reject + 目标环节 + 原因 + 审核人）

另初始化 3 个权限码：`pipeline:view` / `pipeline:edit` / `pipeline:review`（供功能管理界面分配）。

## 四、状态机与环节同步规则

```
draft → backlog → prd → dev → test → verify → review → done
任意环节可 reject → rework（打回目标环节后其后续全部待办）
draft/backlog 可直接 rejected 淘汰
```

| 需求状态 | A 需求分析 | B 产品设计 | C 前端 | D 后端 | E 嵌入式 | F 测试 | G 验证 |
|----------|-----------|-----------|--------|--------|---------|--------|--------|
| draft | doing | todo | todo | todo | todo | todo | todo |
| backlog | done | todo | todo | todo | todo | todo | todo |
| prd | done | doing | todo | todo | todo | todo | todo |
| dev | done | done | doing | doing | todo | todo | todo |
| test | done | done | done | done | na | doing | todo |
| verify | done | done | done | done | na | done | doing |
| review/done/rejected | done | done | done | done | na | done | done |

## 七、已知约定

1. 需求创建后初始状态为 `draft`，需在列表「流转 → 已评估」进入评估环节。
2. 审核通过仅在 `review`（待审核）状态可用；打回可用于任意未终结状态。
3. 嵌入式环节（E）在非嵌入式项目自动置为 `na`（不适用）。
4. 权限码已预置，但**审核接口当前只校验登录**（为保证可用性），如需严格权限控制可在「功能管理」中为角色分配 `pipeline:review` 后再启用后端拦截。
