## 1. 背景与目标

### 1.1 背景
团队已通过 CodeBuddy 搭建多AI员工研发流水线（需求分析师→产品经理→前端/后端/嵌入式→测试→验证→老板审核），但当前全部靠对话驱动，存在：
- 需求状态、进度不可视，老板无法一眼掌握全局；
- 审核依赖对话确认，缺少统一裁决界面；
- 需求池/PRD/测试报告散落在文件系统，缺乏集中查看入口。

### 1.2 目标
在 AI 起爆一体化工具集内新增 `/ai-pipeline` 模块（侧边栏「AI 流水线」），提供：
1. 需求池管理（CRUD + 卡诺/AARRR 标签 + 状态流转）
2. 流水线看板（每个需求走到 A~G 哪个环节，状态灯展示）
3. 交付物管理（PRD/原型/测试报告/审核汇总 在线预览）
4. 审核区（老板对「待审核」需求 ✅通过 / ⛔打回）

### 1.3 非目标（二期 REQ-2026-002）
- AI 自动生成 PRD / 测试用例（需接入大模型 API，另行评估）
- 全流程耗时统计报表

## 4. 功能需求

### 4.1 需求池管理（模块一）

- FR-1.1 新建需求：标题、描述、卡诺分类（M/O/A/I/R）、AARRR 环节（多选：获取/激活/留存/收入/传播）、优先级（P0/P1/P2）、来源。编号自动生成（`REQ-YYYY-NNN`，全库唯一）。
- FR-1.2 编辑/删除需求：仅 `pipeline:edit`；已进入 PRD 后的需求禁止删除（提示先打回）。
- FR-1.3 需求列表：分页 + 关键词搜索 + 筛选（状态/卡诺/优先级/AARRR）。
- FR-1.4 状态流转：状态机 `draft → backlog → prd → dev → test → verify → review → done / rejected`，以及任意状态可进入 `rework`（打回）。状态变更记录时间与操作人。
- FR-1.5 需求详情：展示全字段 + 交付物列表 + 审核历史时间线。

### 4.2 流水线看板（模块二）

- FR-2.1 看板表格：每需求一行，7 个环节列（A需求分析师/B产品经理/C前端/D后端/E嵌入式/F测试/G验证）。
- FR-2.2 状态灯：每环节显示 已完成(绿)/进行中(蓝)/未开始(灰)/打回(红)。仅当需求涉及的环节启用（E 嵌入式可标记 N/A）。
- FR-2.3 看板数据来自环节记录表，可展开查看该环节的操作记录与交付物。

### 4.3 交付物管理（模块三）

- FR-3.1 登记交付物：每个需求按环节登记交付物（标题、类型、文件路径或URL）。
- FR-3.2 在线预览：支持 Markdown（PRD/报告）与 HTML（原型）；其他类型提供下载链接。
- FR-3.3 交付物与环节、时间关联展示。

### 4.4 审核区（模块四）

- FR-4.1 待审核列表：仅展示 `review` 状态需求。
- FR-4.2 通过：需求 → `done`，记录审核人/时间/意见。
- FR-4.3 打回：必须选择打回环节（A~G）并填写原因 → 需求进入 `rework`，原因写入审核记录。
- FR-4.4 权限：审核接口要求 `pipeline:review`，无权限返回 403。
- FR-4.5 审核历史：每个需求完整展示审核/打回记录。

## 5. API 设计（字段级）

> 基础路径 `/api/v1/pipeline`，均需 `Authorization: Bearer <JWT>`。

### 5.1 需求接口

**GET `/api/v1/pipeline/requirements`** 列表
```
Query: page=1&pageSize=20&status=&kano=&priority=&aarrr=&keyword=
Resp:
{ code:0, data:{ total: 12, items:[{
  id:1, req_no:"REQ-2026-001", title:"...", kano_category:"O",
  aarrr_impacts:["retention","activation"], priority:"P0",
  status:"prd", source:"老板", created_at:"2026-08-12 10:00", updated_at:"..."
}]}}
```

**POST `/api/v1/pipeline/requirements`** 新建
```
Body: { title(必填≤200), description, kano_category(枚举), aarrr_impacts(数组), priority, source }
Resp: 创建后的完整对象（含自动编号 req_no）
```

**PATCH `/api/v1/pipeline/requirements/:id`** 编辑（`pipeline:edit`）
**DELETE `/api/v1/pipeline/requirements/:id`** 删除（状态为 draft/backlog 才允许）
**PATCH `/api/v1/pipeline/requirements/:id/status`** 状态流转
```
Body: { status:"prd" }  // 必须符合状态机转移表，非法转移返回 400
```

### 5.2 看板接口

**GET `/api/v1/pipeline/requirements/:id/stages`** 环节时间线
```
Resp: { data:{ stages:[{ stage:"A", name:"需求分析师", status:"done", started_at, finished_at, note }] }}
```

### 5.3 交付物接口

**GET `/api/v1/pipeline/requirements/:id/deliverables`**
**POST `/api/v1/pipeline/requirements/:id/deliverables`**
```
Body: { stage:"B", title:"PRD", file_type:"markdown", file_path:"docs/prd/REQ-2026-001-PRD.md", url:"" }
```

### 5.4 审核接口

**POST `/api/v1/pipeline/requirements/:id/reviews`**（需 `pipeline:review`）
```
Body: { action:"approve" } 或 { action:"reject", target_stage:"B", reason:"验收标准不可测试"(必填) }
Resp: 更新后的需求状态
```

**GET `/api/v1/pipeline/requirements/:id/reviews`** 审核历史

## 7. 非功能需求

- **NFR-1 权限**：审核接口必须校验 `pipeline:review`；其余读写接口校验 `pipeline:view/edit`；无 token 一律 401。
- **NFR-2 兼容性**：不影响现有登录链路（sys_user）与用户管理（user_profiles）；新模块路由 `/ai-pipeline`，与现有路由无冲突。
- **NFR-3 前端规范**：Vue3 + Element Plus，新增页面放 `src/views/pipeline/`，API 封装放 `src/api/pipeline.js`，路由在 `router/` 注册为 `/ai-pipeline`。
- **NFR-4 性能**：列表接口 < 300ms（数据量万级以内）；分页必填。
- **NFR-5 安全**：描述/标题做长度与 XSS 校验；删除接口做状态约束（仅 draft/backlog）。
- **NFR-6 可维护性**：表结构由后端启动自动迁移创建，与现有模式一致；SQL 文件归档 `backend/` 迁移目录。

## 9. 风险与开放问题

| 风险 | 等级 | 应对 |
|------|------|------|
| 交付物预览跨服务器路径解析 | 中 | 预览统一走后端代理接口，前端只拿 file_id |
| 打回语义复杂度（rework 后从哪一环重跑） | 中 | 一期规则：打回指定环节，rework 后该环节及其后续全部置 todo，重新流转 |
| 权限码初始化遗漏 | 低 | 迁移脚本初始化 `pipeline:*` 并绑定 admin 角色，验证脚本覆盖 |
| 原型 HTML 依赖外网 CDN | 低 | 正式实现用 Element Plus 本地包，无 CDN 依赖 |

### 开放问题
1. 交付物预览是否需要做上传（把文件上传到服务器）？一期建议仅登记已有文件路径，二期做上传。
2. 看板是否要甘特/泳道图增强？一期用表格+状态灯即可。
